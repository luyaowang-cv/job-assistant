## 0. 先说结论

你贴的那份报告和"经常超时"其实是**两个独立的病**，别把它们当成一件事：

那次运行顶部写着「已完成 2/2 批」，意思是**接口一次都没失败**。4 项已填写全部来自 glm-5；交给模型的 37 个字段里，它对剩下的 **33 个全部弃权**。根因是**交给模型的字段名本身就是错的**——字段名变成了"女""北京市""年""+86"。模型拿到一堆没有意义的字段名，只能全部弃权（`unresolvedIds`）。

把 33 项"需手动处理"拆开看：

| 原因 | 项数 | 性质 |
| --- | --- | --- |
| 标签识别错了（字段名变成值/选项/空态文案） | 22 | 真 bug，就是"识别不精准" |
| 词表没覆盖（"职责""听说""读写"这类真实标签） | 6 | 规则缺口 |
| 档案里确实没有这个数据 | 5 | 设计如此（到岗时间/公司网站/语言类型/掌握程度/项目名称） |

所以这次的锅 2/3 在标签上，不在模型上，也不在超时上。

而"经常超时、连接失败"是另一条链路，有四个独立的坑叠加：**客户端根本没有超时**、**单批最坏 184 秒且没有总时限**、**一个 400/401 会直接放弃后面所有批次**、**整条链路跑在会被浏览器销毁的 popup 里**。

第二次运行（交银那份，第 7 节）是**另一种病**：标签全对，但一整个教育区块 8 个字段"AI 已给出建议，但页面控件未能应用"。这句话背后藏着八种不同原因（代码把它们合并成了一句），最可能的一条是**自定义下拉的选项从没告诉过模型**——而更危险的是那 5 个「已填写｜是」：单选组的字段名被取成了第一个选项文字（"是"），模型很可能对每个是非题都答了"是"。**请先看 7.4。**

## 1. 一次「AI 填写」实际发生了什么

点「AI 填写当前页面」之后的真实顺序（`entrypoints/popup/main.ts` 的 `fillCurrentPage`）：

1. `scanEveryFrame` 扫全帧拿字段（`main.ts:564`，函数本身在 `main.ts:500`）
2. `buildFillPlan` 用本地规则把档案里已有的字段先填进页面（纯本地，不联网）
3. **再扫一遍**（`main.ts:591`），用 `fieldSignature` 跟第 2 步的结果对账，挑出还需要问 AI 的字段
4. `buildFillBatches` 切批（≤24 字段 / ≤3200 token 预算，`lib/fill-batches.js`）
5. 逐批 POST `/api/v1/form-fill/preview`。服务端每批都**从头**做一遍：查会话 → 读网申档案 → 读个人主档案 → 读简历版本 → 合成文档版本（`resolveApplicationProfileVersion`，含 blocks/references 的解析）→ 拼完整证据（含简历正文，最多 12000 字）→ 调模型 → 校验 JSON
6. 每批结果分两路写回页面（文本控件 / 选择控件），**逐帧** `executeScript`
7. 汇总成你看到的那份报告

这里面 1 和 3 是同一次扫描干了两遍，5 每批都重复读整份档案，6 每批每帧都要重新注入一遍脚本。后面几节展开。

## 2. 识别不精准：报告里那些怪标签从哪来

### 2.1 现象

你报告里的字段名里，这些**不是字段名**，是页面上的其他文字：

`北京市`、`+86`、`女`、`本科`、`硕士`、`物联网工程`、`2024`、`9`、`2027`、`6`、`年`、`月`、`至今`、`暂无选项`、`首页关于我们社会招聘官网`

### 2.2 机制：标签有两个兜底分支，会把"值"当成"名字"

取标签的函数是 `labelFor`（`lib/form-page-bridge.js:124`），它的候选顺序是：

```
element.labels → 包裹它的 <label>(closest('label')) → aria-labelledby → aria-label
→ Formily 元数据 → data-label/aria-describedby → 容器文本 → 前一个兄弟节点文本 → title
```

问题出在两个地方：

**（a）`wrappingLabel` 排在容器之前（第 126 行）。** 单选组在北森/Element 这类组件库里的写法是每个选项各自被自己的 `<label>` 包住：

```html
<label class="ud-radio"><input type="radio" name="gender">女</label>
```

而单选组的描述符是拿**组里第一个 radio** 去取标签的（`form-page-bridge.js:190` 的 `label: labelFor(element)`）。于是**整组的标签 = 第一个选项的文字**。报告里"女"（性别组）、"本科"和"硕士"（两个学历组）就是这么来的。

**（b）容器文本兜底（第 94–105 行）：** 找不到显式 label 元素时，直接取容器的 `textContent`（≤60 字就用）。容器里只要有任何短文字，就会当成字段名。于是：

- 城市下拉 → 容器里显示的当前值 `北京市`
- 区号下拉 → `+86`
- 空下拉 → 空态文案 `暂无选项`
- 导航栏里的搜索框 → `首页关于我们社会招聘官网`
- 专业框 → 当前值 `物联网工程`
- 日期的"至今"分隔符 → `至今`

第 40 行的 `isUselessLabel` 只过滤"年/月/日/至/到/起/止"这类单字和纯符号，**上面这些全都合法通过**。

注意 `nearestContainerLabel`（容器文本）排在 `adjacentLabel`（前一个兄弟节点）**前面**，所以只要容器里有文字，旁边那个真正的标签永远轮不到被读。

### 2.3 实验：只换标签，结果从"填不上"变成"填上"

我用你那份档案的属性重建了这些控件，喂给真实的 `buildFillPlan`：

```
needs_manual  性别单选组，标签="女"     category=unknown   字段含义无法可靠确认。
filled        同一个组，标签="性别"      category=basic     标签与档案栏目匹配。
needs_manual  学历单选组，标签="本科"    category=unknown   字段含义无法可靠确认。
needs_manual  城市下拉，标签="北京市"    category=unknown   字段含义无法可靠确认。
needs_manual  占位符"年"              category=unknown   字段含义无法可靠确认。
```

和你的报告一字不差。**同一个控件、同一份档案，只有标签不同，一个填得上、一个填不上。** 这就是"识别不精准"的完整因果链：标签错 → 本地规则匹配不上（`unknown`）→ 字段被塞进 AI 批次 → 模型看到一个叫"女"的字段，不知道该填什么 → 弃权 → 报告写"AI 也未能给出答案"。

模型没错，是喂进去的东西错了。

### 2.4 次生问题：标签不稳定，导致刚填好的字段被误判成"已有内容"

因为标签有一部分来自"当前显示的文本"，一旦本地规则把值写进页面，**这个字段的标签就变了**（下拉从空态文案变成了选中值）。

而对账用的是 `fieldSignature = [label, name, placeholder, controlType]`（`main.ts:584`）。标签一变，签名对不上，第 3 步的"这是我刚填的"就认不出来，字段会被当成"本来就有内容"。这解释了为什么有些"已有内容，已跳过"可能看着奇怪——它未必是别人填的，可能是**本地刚写进去、然后被自己的签名算法漏掉了**。

这条和 4.1 的"一次填写扫两遍"是同一个根：**标签不是稳定标识，却被当成了稳定标识用**。

### 2.5 日期框为什么永远填不上：`dateUnit` 是死代码

北森的入学/毕业时间是拆开的"年 __ 月 __ 至 年 __ 月 __"，每个小框本身只有"年""月"两个字。规则侧为此留了接口：

- `datePartOf`（`form-fill-rules.js:513`）会读 `field.dateUnit`
- 但**扫描器从来不产出这个字段**（全仓库只有一处引用，第 521 行是唯一一次读取）

更麻烦的是，即使补上 `dateUnit` 也没用，因为 `dateRoleOf`（第 496 行）只看控件**自己**的文字（label/name/placeholder），**不看 context**。北森把"入学时间"写在区块标题上，小框自己只有"年"，role 永远读不出来。实测：

```
needs_manual  年 框（只有占位符"年"）                    字段含义无法可靠确认。
needs_manual  年 框 + dateUnit=year                   字段含义无法可靠确认。
needs_manual  年 框 + dateUnit=year + 上下文含"入学时间"   字段含义无法可靠确认。
filled        年 框 + name=educationStartYear           value="2024"
filled        月 框 + name=educationStartMonth          value="9"
```

结论：**只有 ATS 把 role 和单位都写进 `name`（如 `educationStartYear`）时这条路才通**。北森的 name 是另一套命名，所以这一整类字段（报告里有 16 个标签是"年/月/至今/2024/9"这类日期分片，占 33 项的一半）必然全灭。要修得两处一起动：扫描器补 `dateUnit`（可以从相邻的单位字符读），`dateRoleOf` 允许从 `context` 读 role。

### 2.6 值得你亲自核对的一个怀疑：空下拉被当成"已有内容"

`hasValue` 的判定是 `Boolean((element.value ?? element.textContent ?? '').trim())`（第 237 行）。对原生 `<select>` 来说，**只要没有任何 option 带 `selected`，浏览器会自动选中第一个**，`select.value` 就等于第一个选项的值（没写 value 属性时就是它的文字）。

所以一个"看起来空着"的下拉，只要第一个选项是真实值而不是 `<option value="">请选择</option>`，就会被判定为**已有内容**、静默跳过。

你的报告里有一行「已有内容，已跳过｜暂无选项」——"暂无选项"正是空下拉的空态选项文案。这基本可以认定是同一个坑。**15 项"已有内容，已跳过"里可能有一部分其实是空的，被白白跳过了**，而且报告上完全看不出来。

附录 A 第 2 段脚本能直接确认。

### 2.7 词表缺口（这 6 项的标签是对的）

`职责`、`项目中职责`、`听说`、`读写`、`公司规模`、`推荐码` 的标签是**正确**的字段名，是规则没覆盖：

- `work.description` 的别名有 主要职责/岗位职责/工作职责，**没有裸"职责"**（`form-fill-rules.js:181`）；`project.description` 有"项目职责"但没有"项目中职责"（第 190 行）
- 语言能力的"听说/读写"四列没有对应规则：`languages.detail`（第 212 行）只认"语言水平/掌握程度/熟练程度"这类说法，不认列的语义
- 公司规模归 `work.company` 的否决规则里去了（第 563 行），但没有对应字段可填
- 推荐码、公司规模本来就不该由模型编，留空是对的，只是文案可以更清楚

## 3. 经常超时 / 连接失败

### 3.1 客户端根本没有超时

`readApi`（`main.ts:345`）就是裸 `fetch`，没有 `AbortSignal`、没有 `AbortController`、没有总时限。服务端连接挂住或网络静默丢包时，浏览器自己的超时是以分钟计的，弹窗会一直停在「AI 正在填写…」，按钮一直是 disabled，没有任何出路，也没有"取消"。

这一条最像你说的"卡住的感觉"。

### 3.2 单批最坏 184 秒，而且没有总预算

服务端（`web/server/services/form-fill-provider.service.ts`）：

- `PROVIDER_TIMEOUT_MS = 60_000`（第 12 行）
- `MAX_FILL_OUTPUT_TOKENS = 4_096`（第 22 行），**并且没有开 stream**（第 58 行的 fetch 里没有 `stream: true`）

非流式 + 4096 输出 token，意味着模型必须把整段 JSON 生成完才回第一个字节。输入侧还要先吃完最多 12000 字简历正文 + 整份档案 + 24 个字段的提示词。首 token 慢一点、答案长一点，60 秒就没了。

插件端（`main.ts`）：

- `FILL_BATCH_ATTEMPTS = 3`（第 43 行）、`FILL_RETRY_DELAYS_MS = [1000, 3000]`（第 45 行）
- `AI_PROVIDER_TIMEOUT` 是**可重试**的（第 90 行的白名单）
- 失败后**不 break**，下一批继续（第 688 行只对不可重试的错误才 break）

于是**一批**的账是：60s → 等 1s → 60s → 等 3s → 60s = **184 秒**，然后继续下一批，每批都能再烧一遍。`MAX_FILL_BATCHES = 60`（第 40 行）是防失控的护栏，不是目标，但**没有任何总时限兜底**——最坏情况是弹窗开着几十分钟。

### 3.3 一个 400 就会放弃后面所有批次【已证实】

扫描器给 contenteditable 富文本框（北森的自我评价、项目描述就是这类）填的 `controlType` 是**标签名**：

```js
controlType: element.tagName.toLowerCase()   // form-page-bridge.js:234
```

contenteditable 的 div 会变成 `'div'`，而服务端的枚举里没有这个值：

```
[FAIL] contenteditable 描述框 (controlType="div")
       400 VALIDATION_ERROR -> path=["fields",0,"controlType"]
       msg=Invalid option: expected one of "input"|"textarea"|"select"|"radio-group"|"custom-select"
```

`VALIDATION_ERROR` 不在 `RETRYABLE_CODES` 里，`isRetryable` 也要求 `!error.code`，所以它被判定为"不可重试" → `main.ts:688` 的 `break` → **表单剩余部分全部不跑了**。用户看到的是「工作台请求失败（HTTP 400）」，实际上一整页都没填。

同一路径上还有 **401 会话过期**（`web/server/middleware/auth.ts`）：Nitro 抛的 401 响应体不是 `{ error: { code } }` 这个信封，`body.error?.code` 是空串 → 同样不可重试 → 同样 `break`。用户看到「工作台请求失败（HTTP 401）」，文案对用户没有任何可操作性（不知道该去重新登录）。

实测同一份 schema 的其他边界：

```
[FAIL] 模型返回 value 长度 4001        -> 整个批次作废（重试 3 次也必失败）
[FAIL] 模型返回空字符串 value          -> 整个批次作废
[FAIL] 模型多返回一个 note 字段        -> 整个批次作废（.strict()）
```

后三条都在服务端 `modelFormFillResponseSchema` 上：模型偶尔多加一个字段、或写超 4000 字，整批就废，而且会被**当成可重试**再打两遍。这是 429 和"重试也没用"的一个隐形来源。

### 3.4 中断之后的报告会撒谎

被 `break` 掉、从没跑过的批次，它的字段最后落到这个兜底文案（`main.ts:716`）：

> `… ；AI 也未能给出答案。`

**"没问过"被写成了"答不出"**。字段级的结论因此不可信——你以为模型看过这些字段，其实根本没发出去。（顶部汇总里有一句"已完成 x/y 批"能对出来，但逐字段的结论误导性很强。）

### 3.5 每批都重新加载整份档案

`preview.post.ts` → `previewAiFormFill` 每批都要：

1. `getApplicationProfileFillContext`：网申档案、个人主档案、简历版本各查一次，命中 `currentVersionId` 时还要跑一遍 `resolveApplicationProfileVersion`（版本 + 组合数据 include + 再查一次主档案 + 解析 blocks/references），合计 6 次以上数据库读取和一次文档合成
2. `getAiProviderRuntime`：再一次数据库查询，并且每次都要重新解密 API Key
3. 重新拼证据（`buildFillEvidence`），并把最多 12000 字简历正文**再上传一遍**

这些结果在**同一批字段的整个填写过程里是恒定的**，却被逐批重算。

批数越多重复越多。叠加插件端 3 次重试，实际请求量还会翻倍到 3 倍——这是 429 的直接来源。

### 3.6 整条链路跑在 popup 里，失焦即销毁【已证实】

`extension/entrypoints/` 里只有 `popup.html` 一个入口，没有 background / service worker，没有 side panel。浏览器扩展弹窗**一旦失焦就被销毁**：

- 你点一下网申页面想看看填到哪了 → 弹窗关闭 → 正在 await 的 fetch 和整个循环一起消失
- 弹窗里的 chrome.storage 逻辑（`wxt.config.ts` 的注释也写了"popup closes whenever the user goes back to the page"）说明作者知道这个特性，但**填写主流程本身没有搬出去**

这是个架构级问题：越是想盯着看，越容易把它杀掉。

## 4. 慢 / 卡顿

### 4.1 一次填写扫了 4 遍全帧

`scanEveryFrame`（`main.ts:500`）内部是 2 个 `allFrames` 注入（取字段 + 数 iframe），而 `fillCurrentPage` 调它**两次**（第 564 行和第 591 行）。合计 4 次全帧注入，每次都要在**每一个 iframe**（含广告、统计、客服、验证码 iframe）里跑一遍完整扫描。北森的表单本身就在 iframe 里，周边还挂着一堆第三方 iframe。

### 4.2 扫描本身就是重活

每个控件的取标签过程（`form-page-bridge.js`）：

- `semanticContainerFor`（第 57 行）最多上溯 5 层，每层 `querySelectorAll` + `getComputedStyle` + `getBoundingClientRect`
- `nearestContainerLabel`（第 94 行）里那个选择器带 `[class*="label"]`——**子串属性选择器无法用任何索引**，等于对容器整棵子树扫一遍，然后对每个候选再调一次 `shortVisibleText`（又一次 `getComputedStyle` + `getBoundingClientRect`）
- `contextFor`（第 141 行）把 `labelFor` 和 `semanticContainerFor` **又算一遍**

按控件算，是几十次强制样式读取，一整块同步 JS 跑在主线程上。几百个控件的表单上，这是几百毫秒到秒级的卡顿，而且是在**每个 iframe 里各来一遍**。

### 4.3 写入器里全是固定 sleep

| 位置 | 常量 | 每个字段/控件耗时 |
| --- | --- | --- |
| `form-page-bridge.js:305,310` | `REVEAL_MS=90` + `COMMIT_SETTLE_MS=48` | 每个文本控件 138ms |
| `:313` | `BATCH_AUDIT_MS=120` | 每批一次 |
| `:541,542` | `REVEAL_MS=90` + 2×rAF + 140ms | 每个自定义下拉 ~230ms |
| `:644` | 点选项前再等 120ms | 每个自定义下拉 +120ms |

一批 24 个文本框 ≈ **3.3 秒纯等待**，一个自定义下拉 ≈ 500ms。再加上 `scrollIntoView({ behavior: 'smooth' })` 的滚动动画。

更糟的是文本写入器和选择控件写入器是 `Promise.all` **并行**跑的，两路都在 `scrollIntoView`、都在改背景色——**两边抢滚动位置**，页面看起来就是自己在乱滚、乱闪。这是"页面卡顿"最直接的来源。

### 4.4 批间 400ms 节奏 + 逐帧串行写回

`FILL_BATCH_PACING_MS = 400`（第 51 行）是批间隔；`applyEveryFrame` 对每个帧是 `for await` **串行**注入。帧一多，写回时间线性叠加。

## 5. 已经做对、别误伤的地方

这份代码里有不少明显是踩过坑才写出来的东西，修的时候不要一起推翻：

- **不覆盖已有值**（`skipped_existing`）、敏感字段/上传控件排除、身份证规则的豁免设计

- **报告区分原因**：把"档案里没有"和"模型答不出"分开写，方向是对的（只是被 3.3/3.4 破坏了）
- **重试白名单**：分清 429（会自己好）和 key 失效（永远不会好）
- 服务端的 `isAiFillEligibleField` 白名单（密码/验证码/银行卡/隐私/上传类字段根本不会发给模型）

还有：33 项里有 5 项（到岗时间/公司网站/语言类型/掌握程度/项目名称）**档案里确实没有这个数据**，留空是正确行为；"推荐码""公司规模"这类也不该让模型编。这部分不用改。

## 7. 第二次运行（交银亲属信息表）：另一种失败模式

这一份报告的症状和第一次完全不同，值得单独记一节。

### 7.1 这一次的标签是对的

学历、学校名称、专业名称、学位、学习形式、研究方向、在校期间成绩排名、是否在职期间获取——全是**真实字段名**，不是上次那种从页面文字里捞来的值。说明第 2 节那个"标签被值污染"是**页面相关**的（北森/牛客那套组件的写法触发的），不是普遍性故障。

反过来讲：**修标签不会解决这个页面。这个页面的病在写入。**

### 7.2 「未能应用」这句话吞掉了八种不同的原因

「AI 已给出建议，但页面控件未能应用」只在 `main.ts:697` 一处生成，触发条件是"这个 fieldId 进了 `unavailableIds`"。而往 `unavailableIds` 里塞东西的地方有八处，报告里全都显示同一句话：

| 真实原因 | 位置 |
| --- | --- |
| 这个 id 在页面上**已经找不到对应控件**（DOM 变了、位次变了） | `form-page-bridge.js:499` |
| 整帧注入失败（iframe 被销毁 / 换页 / 跨域） | `main.ts:542`，而且 `catch {}` **连日志都没有** |
| 原生下拉找不到唯一匹配项 | `form-page-bridge.js:444` |
| 文本框写进去之后被框架回滚（含 120ms 后的复查） | `:482`、`:369` |
| 复选框点击没生效 | `:395` |
| 控件在写入时是 disabled / readonly | `:405` |
| 单选组：组内有禁用项 / 选项文字对不上 / 点击后未选中 | `:572`、`:581`、`:588` |
| 自定义下拉：展开后没找到唯一选项 / 选完读回不一致 | `:639`、`:648` |

所以"未能应用"这四个字，**目前既不能让你知道该改什么，也不能让你知道要不要重试**。就你眼前这两次运行而言，先把这句话拆开（把原因写进报告）比修任何一个具体 bug 都更值——否则每次出问题都要重新猜一遍。

### 7.3 为什么整个教育区块 8 个字段一起失败

按可能性从高到低：

**① 自定义下拉的选项，对模型来说是空的【代码可证实】**

扫描器给 `custom-select` 的 `options` **永远是 `[]`**（`form-page-bridge.js:220`），而单选组是带上选项文字的（`:196`）。于是模型对单选组知道有哪些选项（那 5 个"是/否"就成功了），对自定义下拉**只能猜一个字符串**。

写回时（`:619-641`）只做三件事：点开容器 → 等 2 帧 + 140ms → 在页面上找 `.ud__select-option` / `[role="option"]` 这类元素。**全程从不输入关键字。** 于是：

- 远程搜索型下拉（学校、专业、研究方向基本都是）**必须先输入才会出选项** → 一个选项都找不到 → 未能应用
- 就算出选项，140ms 也可能不够（异步取数据 / 展开动画）

学历、学位、学习形式、iTalent 的学校-专业级联都属于这一类。**这一条能单独解释这 8 个字段，而且只看代码就能确认。**

**② 位次 id 在写入时已经错位【需要探针确认】**

所有 id 都是"控件在 `querySelectorAll` 结果里的位次"（`form-field-N` / `custom-select-N` / `radio-group-N`）。从第二次扫描（`main.ts:591`）到真正写回，中间隔着模型调用——**几秒到几分钟**。这期间只要页面 DOM 增减一个节点（展开一个下拉、条件字段出现、框架重渲染），**后面所有 id 全部错位**：写不进去（`:499` → 未能应用），或者更糟，**写到别的控件上**。

代码注释自己就写着这件事："or `form-field-N` stops naming the control the plan was built for"（`form-page-bridge.js:9`）。判别方法：附录 C 的 STEP 1 / STEP 2。

**③ 两路写回并发互扰**

文本写入器和选择控件写入器是 `Promise.all` **同时**往同一个 frame 注入（`main.ts:672`）。一路在点开下拉、一路在 focus→写值→blur。下拉被另一路的动作打断或关掉，表现出来就是"展开了但一个选项都没有"。

**④ 这一帧失效了**

如果是多步表单或区块异步挂载，`executeScript({ frameIds: [旧 frameId] })` 会直接抛错，整帧条目被标成 unavailable（`main.ts:542`）——**错误被吞掉、没有任何日志**。判别方法：附录 C 的 STEP 3 会标出这些控件是否在 `<iframe>` 里。

### 7.4 更值得警惕的：那 5 个「已填写｜是」

6 个"是"（5 个已填写 + 1 个已有内容）很可能**不是填对了，而是第一次那个标签 bug 换了个面孔**。

单选组的标签取的是**第一个选项的文字**（`form-page-bridge.js:190`）。所以一组"是/否"的字段名就变成了 **"是"**。模型收到的是这样一个字段：

```json
{ "label": "是", "controlType": "radio-group", "options": ["是", "否"] }
```

字段名叫"是"，选项里也有"是"——模型最省力的回答就是"是"，写回时又能精确匹配到选项（`:581`），于是**报告显示"已填写"，页面被勾成"是"**。

**请务必核对这 5 个问题分别问的是什么、答案是不是都该是"是"。** 亲属信息这类表里，"是否有亲属在交银集团工作"这一项答错是有实质后果的。

第一次的标签 bug 表现成"填不上"（你看得出来），这一次表现成"填错了但显示成功"（你看不出来）。**后者更危险**，而且它现在是静默的。判别方法：附录 C 的 STEP 3 会把每个"是/否"组的**真实提问文字**打出来。

### 7.5 其余几条

**本人承诺……（×2）**：这是一个复选框，标签是整段承诺文字，规则里没有对应栏目 → `unknown`。但复选框在**送 AI 之前就被过滤掉了**（`main.ts` 的 aiFields 过滤条件里有 `inputType === 'checkbox'` 一项），所以它从没问过模型，报告里也就只有半句话（没有"AI 也未能给出答案"）。这类承诺框的正确表述应该是"需要你手动勾选"，而不是"字段含义无法可靠确认"。

**未命名字段（×2）**：label、name、placeholder 三者都是空的 → 有意不送 AI（`skipAi`）。典型来源是复合控件的分隔/占位框，或者展开的下拉里那个搜索输入框。

**招聘信息来源 / 个人年薪期望值 (税前含福利)**：标签是对的，是词表和档案的双重缺口。"个人年薪期望值"因为 `normalize()` 会把括号去掉、剩下的字串跟 `basics.expectedSalary` 的任何别名（期望薪资/期望薪酬/薪资期望/期望月薪…）都对不上；而且档案里的期望薪资是月薪。这类字段更适合**本地规则 + 单位换算**，不该指望模型从"年薪"两个字推出来。

## 8. 本次修复（2026-10-12）

第 1–7 节是诊断，这一节是实际改了什么。改动落在 4 个文件、新增 2 个文件（`lib/form-labels.js` 及其测试）；测试从 79 条增加到 96 条，全部通过。

### 8.1 修了什么

**A. 不再静默答错是非题（最重要的一条）**

`lib/form-page-bridge.js` 新增 `radioGroupLabel`：单选组的字段名改成"组容器的文本减去各选项的文本"，减不出问题就**不给它名字**，而不是退回到第一个选项。判定用 TreeWalker 加节点包含/全等比较，**绝不做字符串替换**——把"是"从"是否在职期间获取"里替换掉，会把问题本身吃掉。

**B. 标签不再被"值"污染**

容器文本兜底（`nearestContainerLabel` 的第二分支）从"相邻兄弟之前"降到"之后"；并且只在容器里**只有这一个控件**、容器文本**不等于该控件自身的值或选项拼接**时才允许当标签。新增 `lib/form-labels.js` 收拢"什么不配当字段名"：空态文案（请选择 / 暂无选项 / `--`）、纯数值（2024 / +86）、单位与分隔符（年 / 月 / 至）。规则模块直接 import 它；页面侧扫描器因为要被序列化进页面只能内联副本，`form-labels.test.js` 会断言两边的正则字面量完全一致，漂移即失败。

**C. 日期分片框能填了**

扫描器产出 `dateUnit`（从占位符或紧邻的"年/月"读）和 `dateRole`（向上最多 5 层找"入学时间 / 毕业时间"这类区块文字；某一层同时提到两端就放弃，不猜）。规则侧的 `dateRoleOf` 优先用 `dateRole`，并允许从 `context` 的首段读 role。

已知仍未解决：整块只写"起止时间"、靠顺序区分起止的表单依然填不上——它保持人工的状态，不会被写错。要修得按顺序推断，风险大于收益，这次没做。

**D. 写回失败带上原因（可观测性）**

两个写入器都返回 `unavailableReasons`，7.2 表里那八种原因各有各的文案，主流程把它写进报告。帧注入失败不再是 `catch {}`：会 `console.warn`，并把"这一帧注入失败（原因）"写进报告。以后再看到"未能应用"，会同时看到是哪一种。

**E. 下拉：先输入关键字，再找选项**

`applyChoiceEntries` 在点开下拉找不到唯一选项时，会把答案**输入**到下拉自己的搜索框（原生 setter + `input` 事件），等 320ms 再看一次。学校名称、专业名称这类远程搜索型下拉以前必然失败。输入后仍然没有可选项时**不清理输入框**，理由写成"已在下拉框里输入答案，但页面没有给出可选项，需要你手动确认选哪一项"。

**F. 不再因为一个 400 丢掉整张表**

contenteditable 的 `controlType` 从标签名归一成 `textarea`（服务端枚举里没有 `div`，这一条就是那个 400）。批次失败的处理从"不可重试就 break"改成"只跳过这一批"，只有**必然对每一批都失败**的错误（密钥无效 / 未配置、401、403）才中止，并给出可操作文案（"工作台登录已过期，请先打开工作台重新登录"）。连续 3 批同一个原因失败才停下，避免在系统性错误上空转到预算耗尽。

**G. 超时与总预算**

`readApi` 加 75 秒超时（服务端 60 秒就会回自己的错误，比客户端超时有信息量），超时归为可重试并有独立文案。整个填写有 8 分钟总预算，每次请求的超时取"剩余预算"与 75 秒的较小值，绝不超支。没跑过的批次单独标记，报告写"本次没有询问 AI（原因）"，不再冒充"AI 也未能给出答案"。

**H. 词表**

`职责` → `work.description`，`项目中职责` → `project.description`。前者会不会误伤项目块里的框，由区块闸门挡住，测试里有对照用例。

**I. 空下拉不再被误判"已有内容"**

`selectHasValue`：选中项是空态文案或 value 为空即视为没填。**故意没做**更激进的"`selectedIndex > 0` 才算有值"——一个开在 1990 年的年份下拉，和一个被填成 1990 的下拉，从 DOM 上分不出来，宁可不覆盖。

**J. 两个既有的类型漏洞**

`FillEntry` 补上 `skipAi`；`buildFillBatches` 的返回值在调用处标成 `FormFieldDescriptor[][]`，顺带消掉 4 条既有 TS 诊断。

### 8.2 怎么验证的

`node --test lib/*.test.js` → **96 passed / 0 failed**（原 79 条 + 新增 17 条：`form-labels.test.js` 12 条，规则测试 5 条）。

## 9. 第二轮修复：准确度（2026-10-12 晚）

按"少数站点做深、先把准度做上去"的方向，这一轮做的是**答案记忆**和**是非题约束**。测试 96 → 113 条，全绿。

### 9.1 为什么先做这两条

第 7 节的第二次运行里，"需手动处理"的字段分三类，其中两类是**每家公司都会重复问的**：是非题（是否有亲属在交银集团工作…）、档案里没有的偏好（招聘信息来源、个人年薪期望值、本人承诺）。它们在每一张表上都要人工处理一次，而且**模型对它们是掷硬币**——第二次运行里 6 个"是/否"组被答成"是"就是这么来的。

所以这两条一起做，效果是互补的：**是非题不再让模型猜（消除静默错答），你确认一次之后被记住（消除重复劳动）**。

### 9.2 答案记忆（`lib/answer-memory.js`）

存在扩展本地（`chrome.storage.local`），不经过服务端。三条边界是设计的一部分：

- **只有人放进去的答案才会在里面。** 模型猜的一律不记，所以一个错误答案不会变成永久答案。
- **档案能回答的问题永不记录。** 那些字段每张表都由档案事实填，缓存它们只会多出一个更旧的第二真相源。
- **答案能走多远取决于它是什么。** 是非题（"是否有亲属在本公司工作"）和叙述题（"为什么选择我们公司"）只在你填过的那家站点复用；偏好类（招聘信息来源、年薪期望）跨站点通用。

容量 400 条，按最近使用淘汰；弹窗里逐条可删、可一键清空，每条都标着"通用"还是"只在某站使用"。

**关于读页面值这件事**，我把边界写进了代码注释：`scanVisibleFormFields` 一直遵守"不保留页面输入"（只报 `hasValue`，不报值）。收集器 `collectControlValues` 是唯一读值的函数，**它只在点击"记住我在这页补填的答案"时才运行**——因为静默吸走页面预填内容会把证件号、页面默认值一起存进去。更关键的是**记什么由规则决定**：把这一页的所有值清空后重跑一遍规则，凡档案本就能提供的字段一律不记（敏感字段同理），所以"页面预填的默认值"和"身份证号"都进不了库。

### 9.3 是非题不再交给模型

`lib/field-shape.js` 判定"只有是/否两个选项"的问题（是/否、有/无、Yes/No、同意/不同意，以及复选框）。这类问题**在规则层就被标成 `skipAi`**：档案里没有判断它的事实，模型只能掷硬币，而掷硬币的结果在报告里和"答案"长得一模一样。

报告文案改成："这是是非题，档案里没有可以判断它的事实，需要你自己确认（确认一次就会被记住）。"

男/女、是/否/不确定 这类**不会**被误判（`field-shape.test.js` 里有正反例）。有规则覆盖的是非题（比如"无实习经历"）照常由档案回答。

### 9.4 填写时怎么用

记忆命中发生在**本地那一趟**（和档案事实一起写），所以：不调模型、毫秒级、不会被 AI 覆写，而且报告里会写"来自你记住的答案"。命中过的条目会累加使用次数，长期用不到的会被淘汰。

### 9.5 预期效果，以及它解决不了什么

- 第一张表：这些字段还是要你手工处理一次（而且要在页面上填完后再点一次"记住"）。
- 第二张表起：同样的问法不再出现，直接填上。**这是"少数站点做深"的主要收益来源。**
- 它**不提升**首次填写的准确度——那需要第 6 节里"流式单次请求"（让模型看到整张表）和"站点/选择器记忆"。这两条还没做。

### 9.6 这一轮新增/改动的文件

新增 `lib/field-shape.js`（字段形状判定）、`lib/answer-memory.js`（答案库）、以及各自的测试文件；`lib/form-page-bridge.js` 新增 `collectControlValues`；`lib/form-fill-rules.js` 加是非题闸门；`entrypoints/popup/{main.ts,popup.html,style.css}` 接上入口与管理列表。

## 10. 「连接不稳定」到底是什么（2026-10-12 深夜）

现象：`AI 填写中：第 2 / 14 批…（连接不稳定，第 1 次重试）`，而且"以前从来不会这样"。

### 10.1 那句话在撒谎

`（连接不稳定，第 N 次重试）` 是**所有可重试失败**共用的文案（`main.ts` 的 `onRetry`）。它覆盖的实际情况至少有五种，含义完全不同：

| 真实原因 | 该等的时长 | 该做什么 |
| --- | --- | --- |
| 上游每分钟限额（HTTP 429） | 一个限额窗口，几十秒量级 | 等满再发，别硬撞 |
| 模型回答被截断（4096 token 上限） | 不用等 | 改小批次或开流式 |
| 上游暂时不可用（5xx） | 几秒 | 重试一次 |
| 连接掉线（fetch 抛错） | 一两秒 | 重试 |
| 工作台卡住（超过客户端超时） | —— | **不该重试** |

所以第一步不是修，是**让它说实话**：进度行现在会直接写出错误原文，例如「第 1 次重试：AI 服务请求过于频繁（HTTP 429），请稍后重试。」下次你就能一眼看出是哪一种。

### 10.2 三处确实是错的，已改

**退避时间对不上错误种类。** 原来所有失败都等 1 秒、3 秒，注释还写着"long enough for a per-minute limit to free a slot"——**3 秒绝不足以让每分钟限额重开**。结果不只必然再失败一次，还等于在正在被限流的上游上再打两次，把一个 429 放大成一串。现在 429 走 15 秒 / 30 秒，掉线仍走 1 秒 / 3 秒。

**客户端超时离服务端上限太近。** 服务端给模型的时限是 60 秒，我把客户端设成了 75 秒——只差 15 秒，还要再扣掉工作台自己的数据库与文档合成时间。**它有可能掐掉正要成功的长回答**。现在提到 100 秒。

**客户端超时不该重试。** 能等到 100 秒，说明工作台在它自己 60 秒的上限之后还在算，重发就是再花 100 秒、再调一次模型，问同一个卡住的问题。现在这一批直接记为失败，把时间留给剩下的批次。**注意是我上一轮引入的 75 秒超时本身就可能造成你看到的"第 1 次重试"**——这一点必须算在我头上。

### 10.3 为什么"以前从来不会这样"（推断，待你确认）

第一轮修复之前，一个 400（contenteditable 的 `div`）会让整次填写**放弃剩余所有批次**。现在它会跑完全部 14 批。也就是说：**同一次填写发出的上游调用比以前多得多**，而上游的每分钟限额一直在那里——只是以前被"提前放弃"掩盖了。

这条是推断，不是实测。用新的进度行跑一次，把错误原文发我，就能确认是 429 限额还是截断。

### 10.4 结构性原因（这才是根治的地方）

一张表被切成 **14 批**，就是 **14 次调用**；每次都要重发一遍约一万字的档案（第 9 节量过：6.3k 字简历 → 单批 13.9k 字 ≈ 8.7k–10.7k token），每次都是**非流式 + 60 秒上限**。这个形状本身就不稳：调用越多，撞限额的概率越高；非流式，越长的回答越容易撞超时和被截断。

批次的初衷（一批失败不牵连全表）是对的，但**不该用"切小"来实现，该用"流式"来实现**：一次请求、逐字段返回、边收边写。这样调用数从 14 降到 1，答案长度不再受单次上限约束，中途断了已完成的也保住。这条仍然没做，是下一步最大的一项。

### 10.5 站点适配：为什么不能靠猜

你想给北森/牛客/飞书/Moka 各做一份手工映射，方向是对的——这也是别的插件在这些站点上更准的原因。但**映射表里必须是真实字段名和真实选择器**。我手里只有你两次运行报告里的标签（"推荐码"、"北方工业大学…添加学校全称"），没有这几家 ATS 的 DOM 结构；按"大概是这么写的"去编一张表，结果是**静默填错格**，比现在更糟。

所以加了一个按钮：**「导出当前页字段结构」**。它把当前页每个控件的 `label / name / placeholder / controlType / options / 是否有值 / dateUnit / dateRole` 复制成 JSON（**只带属性，不带你已经填的值**）。

做法：每家 ATS 打开一个网申表单 → 点一次这个按钮 → 把剪贴板内容发我。四家各一次，我就能把映射写成 `lib/ats-sites.js` 里的**按域名生效的规则**（字段名 → 档案栏目、下拉是原生还是要输入才出选项、日期是不是拆开的年月、性别/学历那类单选组的问题在哪一层），这些站点上就不再依赖模型猜。

## 11. 第一份站点结构（北森 `camzhaopin.zhiye.com`，88 个控件）

你导出的那份结构直接暴露了三处问题，其中一处是这次最值钱的发现。测试 113 → 120 条。

### 11.1 十五个"字段名"其实是它自己的值

88 个控件里有十五个的 `label` 是**框里当前显示的值**：`北京市`、`硕士研究生`、`本科`、`应届毕业生`、`中国大陆`、`邯郸市`、`熟练`/`一般`/`了解`、`15001～25000`、`计算机·网络·技术类`、`一个月内`、`身份证`。真名都在 `context` 开头：`意向工作地点北京市北京市北京市`、`学历硕士研究生…`、`掌握程度熟练…`、`期望月薪(税前)15001～25000…`。

机制是第 2.2 节里那条 `wrappingLabel`：北森把选中的值放进控件自己的 `<label>` 里，而取标签的候选链上"包裹它的 label"排在真名元素前面。

改法：**控件当前显示的值永远不算它的名字**。`labelFor` 在挑之前把等于显示值的候选过滤掉，容器里那些 `[class*="label"]` 候选同理。注意只对"当前值的文本"生效：`<label>` 包着一个**空**输入框时它仍然是名字，这条常见写法不受影响。

### 11.2 顺带挖出一个更隐蔽的：段落上下文被"封顶 1 分"废掉了

`scoreRule` 的最后一步是 `Math.min(total, 1)`。当标签**精确命中**时基础分已经是 0.99，那几个加分（段落提示、控件类型、日期关键词）全部被压回 1.0——**两个候选同分，先出现的那条赢**，而 `RULES` 里教育排在实习、项目前面。

后果在这份页面上非常具体：**6 个"开始时间"、5 个"结束时间"里，教育以外的全被算成教育经历**。你档案里只有 2 段教育，于是第 3 个框开始报"档案中没有第 N 条对应记录"，而实习和项目的日期**永远填不上**——这正是"准确度低"里最难查的一类，因为它看起来像"档案里没有数据"。

改法：不封顶。阈值 0.68 是"够不够格"的下限判断，不是概率，分数只用来排序候选。

回放验证：现在 `开始时间`/`结束时间` 按区块正确落到 `work.startDate`/`project.endDate`，记录序号也对上了。

### 11.3 档案里一直有、规则从来没读的两个字段

`strategy.recruitmentSource` 和 `strategy.referralCode` 在档案 schema 里本来就有（`web/server/schemas/application-profile.ts:28`）。第一次报告里的「招聘信息来源」「推荐码」就是它们——**答案在档案里，规则没去读，于是每次都判成"无法确认"**。已补规则。

顺带补的：`生源地` → 籍贯（北森不叫籍贯）、`职务` → 项目角色/职位；另外把「使用时间总计」「技能描述」标成 `noAnswer`：`skills` 是一个扁平的技能名数组，档案里**没有**每项技能的使用时长和描述，9 行交给模型就是 9 个编出来的数字。

### 11.4 「至今」不是是非题

北森渲染 `开始时间 / 结束时间 / □至今`，那一格由「该条记录的结束时间是否为空」推导，属于事实而不是问题（上一轮我把它当是非题拦下来，是个错误，已改）。

归属靠**区块锚点**（`单位名称`/`项目名称`）计数，而不是"它上面最近的结束时间框"：真实页面上结束时间通常已经有值，在计划里会被短路成"已有内容"，根本留不下目标信息。这条只有靠页面结构才成立。

只改"没有任何规则认领"的框——**页面上已有的勾选绝不动**（你自己勾过的不该被它取消）。

### 11.5 在你这张页面上实测（回放脚本）

`docs/diagnosis-scripts/replay-dump.mjs` 把你的 dump 喂给真实规则表，不联网、不碰页面：

## 12. 去掉批次：一次请求 + 流式返回（2026-10-13）

这是从第 3 节起就标记的最大杠杆，也是你最早说的"不要按批次来"。

### 12.1 动手前先发现的一件事

这个仓库**已经在生产环境流式返回**了：求职 Agent 的对话（`openai-compatible-text.service.ts` + `career-agent/chat.post.ts`）用 NDJSON 事件流把它做完了。所以：

- **Caddy / Nitro / 部署那一层不用冒险**——那条链路已经被验证过。我一开始准备改 `Caddyfile`（怕 `encode gzip` 把流憋住），看到这个之后**没有动它**，因为同一个栈上的流式对话已经在跑。
- 有现成的写法可以照抄：`content-type: application/x-ndjson`、`cache-control: no-cache, no-transform`、`x-accel-buffering: no`、`sendStream`、上游 `stream: true`、错误也作为事件下发、`cancel()` 取消上游。

### 12.2 改了什么

**服务端**
- `server/utils/ai-stream.ts`（新增，纯函数）：SSE 帧的增量切分、`finish_reason` 读取、以及**"把已经写完的答案摘出来"**——回复是自左向右写的，所以每个 `{"fieldId":…,"value":…}` 的右花括号一到就能用，不必等整个文档。它要正确处理「字符串里的花括号」「被切成两半的帧」「转义引号」，这三件事都有测试。
- `streamAiFormFill`：整张表一次调用（`stream: true`，`max_tokens: 12000`，超时 240 秒），把答案**边写边下发**；确定性的答案（档案直接命中的那些）先发，因为它们不用等模型。没配 `response_format`——这个仓库另一个流式调用也没用，而抽取器不在乎回复是不是一个规整的 JSON 文档，配置项只是多一个兼容风险。
- `POST /api/v1/form-fill/stream`（新增）：NDJSON 事件流，`fill` / `warning` / `error` / `done`。**批次的 endpoint 原样保留**。
- 顺手把数据库层改成惰性 import：`lib/prisma` 在 import 时就要求 `DATABASE_URL`，所以 `form-fill-provider.service.ts` 以前**无法被测试进程加载**（这也解释了为什么它的算术一直没被测过）。改完之后服务层测试才跑得起来——这个仓库另一个流式服务早就这么做了。

**插件**
- 一张表**一次请求**；答案每攒够 8 条或 700ms 就写一批进页面，而不是等到最后。
- **回退**：如果整条流**一个事件都没产生**（代理把响应憋住了、服务端还没更新、请求在第一个字节前就被拒），自动走回原来的批次路径，只是慢。判据是"有没有事件"，不是"有没有填成功"——模型如实答不出来也算事件，不该因此重跑一遍再花一次钱。
- 流的看门狗是**静默 45 秒**，不是总时长：整张表写几分钟是正常的，但一条 45 秒没有任何字节的连接不会突然冒出答案。

### 12.3 验证到什么程度

- **`server/utils/ai-stream.test.ts`：13 条全绿**，跑的是真实模块（我在这个环境里用 node 的类型剥离直接执行，不依赖 tsx）。覆盖：帧被切两半、`[DONE]`/keep-alive、字符串里的花括号、转义引号、答案在右花括号到达时就产出、**确定性答案先于模型的**、**回复在上限处被截断时已写完的答案全部保留**、**请求里没发过的 fieldId 被丢弃**、同一字段重复回答只取第一条、整条流没有可用内容时报错。
- **服务层 `form-fill-provider.service.test.ts`：12 条全绿**（原 6 条 + 新增 6 条），验证接线本身：一次请求且 `stream: true`、`max_tokens`、提示词里带着全部字段、事件顺序、截断保留、id 过滤、429 透传、档案能全答时**根本不调模型**。
- 扩展侧 120 条测试全绿；改后 TypeScript 只剩那 1 条既有诊断（`payload.entries` 那条），无新增。

### 12.4 怎么判断跑的是哪条路

**报告里出现「已完成 N/M 批」就说明走了回退路径**（批次路径才会这么说）。流式成功时不会有这句话。如果一直看到它，说明中间有东西把响应憋住了，把这条告诉我。

### 12.5 这次没解决的

- **一次调用的输出上限**：整张表所有答案要写进 12000 token。超了会在 `finish_reason: length` 处收尾——已写完的都保留（这是流式相对批次的实质好处），剩下的需要再点一次。真正的解法是分片续写（`continue`），还没做。
- **`使用时间总计`/`技能描述` 那类字段**依然按设计不填（第 11.3 节）：档案里没有每项技能的时长与描述，需要的是把技能改成结构化数据（工作台 + 迁移），不是填表逻辑。
- **北森的写入方式**（88 个控件全被当成普通 input，真下拉要点开再选）仍然需要第二份 dump + 一次真机报告才能定，见第 11.6 节。
