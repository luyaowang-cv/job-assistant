# F-049: 区块与记录的稳定定位

> 属于 F-047 总纲的 P0 功能点。目标 G1 中的"串位"场景。

## Goal

网申表单里最常见的结构是**同一个区块重复 N 次**：两段实习、两段教育、三个项目。每个块都要填「开始时间」「结束时间」「描述」，标签一模一样。规则层必须回答"这个框属于第几条记录"，答错就是**把第二段的时间写进第一段**——用户看到的是一份自相矛盾的简历。

实测（两段实习，第一段已填好、第二段空着）：

```
c1 公司名称  filled  "公司0"     record 0   ← 应该是「公司1」
s1 开始时间  filled  "2020-01"   record 0   ← 应该是「2021-01」
```

原因是**记录编号只在"需要填的字段"里数锚点**：已经填过的那两格被 `hasValue` 提前短路，没有进入候选集，于是第二段的「公司名称」成了第一个锚点，被编成第 0 条。用户在真实页面上的操作顺序（先填了一段、再让插件补剩下的）恰好会触发它。

**记录编号必须由页面结构决定，与"哪些格子还空着"无关。**

## User scenarios

- 页面有两段实习，第一段已经手工填过公司和时间，第二段全空。插件只补第二段，且补的是**档案里的第二条**经历。
- 页面三段教育，档案只有两段。第三段留空，报告写明"档案中没有第 3 条对应记录"，而不是把第二段再抄一遍。
- 日期被拆成年/月两个框时，同一条经历的两个框归到同一条记录，不各占一条。
- 用户在两次填写之间改动了页面顺序（删掉中间一段），再次填写时记录的对应关系跟随页面，不残留上一次的编号。

## In scope

- **结构优先的记录编号**：把"数锚点"这一步从"待填字段"移到**全部扫描到的字段**上——已填的、敏感的、规则冲突的字段同样参与编号，因为它们占据着页面结构。编号算完之后，才按字段是否待填去取值。
- **锚点与兜底的一致口径**：有锚点（公司名称/学校名称/项目名称…）时按锚点分块；无锚点时按"同一条规则的再次出现"切段；日期分片按"同一条规则的同名分片再次出现"切段。三种口径都基于结构字段，不再各算各的。
- **多出的块如实报告**：页面块数多于档案记录数时，多出来的块标 `needs_manual` 并说明"档案中没有第 N 条对应记录"，不重复使用已用过的记录。

## Out of scope

- **页面侧稳定身份**（给控件打 `data-*` 并跨扫描复用）。原计划放在这里，核对代码后改由 F-052 处理：F-052 会删掉"填写后重新全量扫描"这一步，届时用写入函数自己返回的 `appliedIds` 就足够，身份匹配可能根本不需要。若 F-052 实施时发现仍然需要，再单独补。
- 跨 iframe 的记录编号（两个 iframe 各自的块不会混在一起）。
- 区块标题的文字聚类（「实习经历 / 实习经验」这类标题的模糊匹配已有 `SECTION_HINTS` 处理）。

## 验收标准

- AC-1：两段实习、第一段已填、第二段空着时，第二段取**第 2 条**记录（公司名、职位、起止时间都与第一条不同）；把哪一段已填这件事反过来，结论同样成立。
- AC-2：两段实习都空时，按页面顺序分别取第 1、2 条（现有行为不退化）。
- AC-3：页面三段、档案两段时，第三段 `needs_manual`，原因为"档案中没有第 3 条对应记录"，且前两段仍各取各的。
- AC-4：日期被拆成年/月时，同一条经历的年与月归同一条记录（不出现"年份取第 1 条、月份取第 2 条"）。
- AC-5：敏感字段（如某段经历里的证件号）或规则冲突字段出现在区块内时，不改变该块的编号。
- AC-6：现有 131 条测试全绿；北森 dump 回放 `filled` 计数不低于改动前。

## Risks and open questions

- **性能**：结构字段也要跑一遍 `bestRuleFor`。字段数在 50 以内时开销可忽略；若将来出现上百字段的页面，再考虑缓存（同一字段在一次 `buildFillPlan` 内只算一次，天然不重复）。
- **敏感字段参与编号**是否会让编号漂移：敏感字段通常不属于可重复区块，纳入编号不会改变锚点计数；但 AC-5 专门锁住它。
- **无锚点页面的兜底**依赖"字段在页面上的顺序"，若某站把同名字段全部集中排列（所有描述框在一起），兜底口径会退化——这类页面本次不额外处理，如实报告为"无法确定第几条"。

## 实施记录（2026-10-19）

**先复现，再改**。改动前用两段实习、第一段 `hasValue: true` 的夹具跑出 `c1 = 甲公司 / record 0`，与预期 `乙公司 / record 1` 不符——用例在旧实现下失败并打印了实际值。

**改法**：`buildFillPlan` 第一趟对每个字段算一次 `bestRuleFor`，命中规则的字段（含已填/敏感/冲突）全部进 `structure`；`assignRecordIndices` 改为吃 `structure`；第三趟取值不变。顺带把 `classifyField(field, match)` 改成可复用外部 match，同一字段一轮内不再打两遍分表。

**顺带修好的报告文案**：块数多于档案时，原来只说「页面中的重复区块多于档案中的记录条数」，现在写明是第几块——「档案里没有第 3 条对应记录，这一块需要人工填写。」

**验收**：AC-1 ~ AC-5 全部通过；测试 131 → **136 全绿**；北森 dump 回放 `filled 5 / skipped_existing 11 / needs_manual 21 / 送模型 3`，与改动前完全一致。

**一处计划调整**：原定在本功能点引入的"页面侧稳定身份"改由 F-052 处理（原因见 plan 与契约）。若 F-052 实施时发现仍需身份匹配，再单独补。
