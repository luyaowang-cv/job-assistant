# F-058: 首页「接下来」日程卡

## Goal

首页概览只有投递的派生指标（今日/本周投递、漏斗、节奏），看不到"哪天该做什么"。投递详情里其实一直有「下一步安排 / 下一步日期」两个字段，但没有任何地方把它们按时间摊开，用户只能靠「今日重点」去记——而今日重点只有停滞天数、不显示具体日期。本次在概览区加第四张卡，把「下一步日期」按时间升序排出来。

## User scenarios

1. 打开首页就能看到最近三条日程：公司、下一步、具体日期（10/24 · 周六），以及「今天 / 明天 / 逾期 2 天」这类相对说法。
2. 逾期没做的排在最前面并标红，不用再翻投递看板才知道漏了什么。
3. 点任意一条打开投递详情弹窗（和「今日重点」同一个弹窗），看完可以直接回投递看板改日期。

## In scope

- `GET /api/v1/dashboard/summary` 返回体新增 `schedule` 块：`items` 与 `total`。
- 取数口径：`Application.nextActionAt` 非空、未软删、状态不是挂了/放弃、逾期不超过 14 天；按 `nextActionAt` 升序。
- 日期标签收敛到 `web/shared/schedule.ts` 一个纯函数里，配单测（`pnpm test:schedule`）。
- 概览区从三列改四列：重点 / 今日投递 / 本周投递 / 接下来；1180px 以下折两行，900px 以下单列。

## Out of scope

- 不做桌面通知/推送：只在页面内可见，逾期标红。
- 不接入面试记录的「面试时间」和岗位的「投递截止日期」：这两个字段目前基本没人填，先把「下一步日期」这个已有入口用起来。
- 不做「标记完成」：清空日程仍然靠去投递看板改「下一步日期」，逾期条目靠 14 天窗口自然退场。
- 不新增数据库模型或迁移。

## Acceptance criteria

- 有日程时最多显示 3 条，按时间升序，逾期在最前。
- 每条显示公司、下一步（没填时退回岗位名）、相对时间和具体日期（`M/D · 周X`）。
- 逾期标红并写「逾期 N 天」；今天绿色、两天内琥珀、更远灰色。卡片头部在有今天/逾期条目时显示「今天 N」「逾期 N」药丸。
- 逾期超过 14 天的记录不进卡片；挂了/放弃的投递不出现。
- 没有任何日程时显示引导文案，指向投递详情里的「下一步日期」。
- 点击任意一条打开投递详情弹窗，不跳转页面。
- `shared/schedule.test.ts` 在 UTC / Asia/Shanghai / America/New_York / Pacific/Auckland 四个时区下结果一致。
- 概览区 1180px 以上四列一行；1180–900 两行（重点整行 → 两张统计卡 → 日程整行）；900px 以下单列。

## Affected contracts

- **扩展**：`GET /api/v1/dashboard/summary`，返回体新增 `schedule: { items: ScheduleItem[], total: number }`，其中 `ScheduleItem = { id, company, title, status, statusLabel, action, at }`（`at` 是 ISO 字符串）。查询参数不变。
- **复用不改**：`GET /api/v1/applications/:id`（弹窗数据源）。

## Risks and open questions

- **取代 F-045 的「概览区三列一行」**：加了第四张卡，列数与断点都变了，F-045 那条验收标准本次作废。
- **date-only 的时区坑**：「下一步日期」用 `el-date-picker type="date"` 提交 `YYYY-MM-DD`，zod 的 `z.coerce.date()` 把它存成 UTC 零点。按本地时区读，UTC+8 会变成当天 08:00，UTC-5 会退到前一天。所以 `shared/schedule.ts` 一律按 UTC 取日历日，再跟浏览器本地的今天比较。
- **「下一步日期」的填写率**：F-045 记录过 `nextAction` 在 110 条投递里填写数为 0。如果这张卡上线后仍然没内容，问题不在卡本身，而在填的地方太深（投递看板的编辑弹窗）。后续可在空状态里直接放一个「安排下一步」入口。
