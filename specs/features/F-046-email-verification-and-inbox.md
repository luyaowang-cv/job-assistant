# F-046: 邮箱联动（邮箱验证、找回密码与求职邮件收件箱）

## Goal

补齐当前的认证基建缺口，并把散落在用户邮箱里的求职邮件自动收进工作台。

现状有两个空洞：`User.emailVerified` 自 F-042 建表起就没有任何代码写过，是个摆设；用户忘记密码后没有任何找回手段。同时，求职过程中最有价值的信号（笔试通知、面试邀约、感谢信、Offer）都躺在邮箱里，需要用户手工誊抄进工作台。

本次做两件事：**阶段 1** 让认证体系完整可用（发验证邮件、找回密码、接口限流）；**阶段 2** 打通"邮件自动进工作台"的管道（每个用户一个专属转发地址，邮件经 Cloudflare 进来落库，在工作台里可见可读）。

**邮件内容的智能解析（识别公司、岗位、事件类型并关联到投递记录）不在本次范围内**——本次只把管道打通并验证它可靠。

## User scenarios

- 新用户注册后收到一封验证邮件；**必须先点开链接完成验证，才能登录**——注册后不会自动进入工作台。存量账号不受此限制。
- 存量账号（策略切换之前注册的）登录后仍能正常使用现有功能，顶栏有一条"邮箱未验证"的软提醒和"重新发送"入口。
- 用户忘记密码，从登录页点"忘记密码"，填邮箱后收到重置链接，点进去设置新密码；重置成功后此前所有旧会话被踢下线。
- 用户在收件箱页拿到自己的专属转发地址（形如 `u-a1b2c3d4...@inbox.offerscoming.cn`），照页面上的三步指引，在 QQ / 163 邮箱里配一条"自动转发到该地址"的规则；此后所有求职邮件自动出现在工作台的收件箱里。
- 用户能翻阅邮件列表与详情（主题、发件人、时间、正文、原始邮件），能删除单封邮件，能关闭收件或重置地址（重置后旧地址立刻失效，需二次确认）。
- 若用户忘了配转发规则，收件箱空态会引导他回到设置步骤，而不是只显示一片空白。

## In scope

**阶段 1：认证基建**
- 接入 better-auth 的 `emailVerification.sendVerificationEmail` 与 `emailAndPassword.sendResetPassword` 两个钩子，走**服务商无关的通用 SMTP 配置**。
- 新增 `/forgot-password`、`/reset-password`、`/verify-email` 三个公开页面（无需登录即可访问），登录页增加"忘记密码"入口。
- 邮箱验证采取**双轨制**：以 `EMAIL_VERIFICATION_REQUIRED_SINCE` 为分界，此后注册的账号必须先验证邮箱才能登录；此前的存量账号保持"可登录 + 顶栏软提醒"。之所以不用 better-auth 的 `requireEmailVerification`，是因为它是全局开关，一开就把存量账号（`emailVerified` 全为 false）一起锁死。
- 把 better-auth 的限流从内存存储改为**数据库存储**，使 `node-cluster` 多进程下限额真正共享；注册、登录、找回密码、重发验证按路径配额度。
- 配置 `advanced.ipAddress.trustedProxies`，保证反代后取到的客户端 IP 不可被伪造请求头污染。
- 新增管理员专用的 SMTP 健康检查接口，用于排查"注册了但收不到信"。
- 补上**生产环境数据库迁移流程**（此前完全没有）。

**阶段 2：收信管道**
- 每个用户一个专属收件地址，token 用 128 位熵随机生成；地址可重置、可停用。
- Cloudflare Email Routing 子域名 + Email Worker 接收入站邮件，经 HMAC 签名后 POST 到站点 webhook。
- 邮件落库（正文、原始 MIME、附件仅元数据），带幂等去重、大小截断与自动清理。
- 收件箱列表页与邮件详情页；导航新增入口。
- 本地模拟投递脚本，使全链路可在没有 Cloudflare 的情况下验证。

## Out of scope

- **邮件内容智能解析**：识别公司名、岗位、事件类型、面试时间，并关联到投递记录。本次只存原始内容。
- **历史邮件回填**：转发规则只对配置之后的邮件生效，不做 IMAP 拉取历史。
- IMAP 直连邮箱（用户交出邮箱授权码的方案）。
- 发信以外的邮件发送能力（如自动回复、群发）。
- 附件内容存储（仅存文件名、类型、大小）。
- 第三方 OAuth 登录（Google / QQ 一键登录）。
- 完整的角色权限体系、账号注销、封禁。

## Acceptance criteria

**阶段 1**
- 开放注册时可完成注册，注册后收到验证邮件；点击邮件链接后 `emailVerified` 变为 true，顶栏提醒消失。
- 分界时刻之后注册的账号：注册响应**不建立会话**（不自动登录）；未验证邮箱前即使手动登录，业务接口也返回 `403`，界面提示去验证邮箱；完成验证后可正常登录使用。
- 分界时刻之前注册的存量账号**不受上述限制**，可以照常登录并使用现有功能。
- 登录页有"忘记密码"入口且不依赖注册开关；走完流程可用新密码登录，旧密码失效。
- 找回密码与重发验证的接口对已注册与未注册邮箱返回**相同**的响应与相近的耗时，不泄露邮箱是否存在。
- 在 `ALLOW_PUBLIC_SIGNUP=false` 时注册仍被拒绝；既有用户登录不受任何影响。
- 限流生效且跨进程：连续超限请求返回 `429`；限流记录的 key 是**真实客户端 IP**，不得出现 `no-trusted-ip`。
- 未登录可访问 `/forgot-password`、`/reset-password`、`/verify-email`，不被重定向到登录页。
- `GET /api/v1/email/health` 仅管理员可调用，返回 SMTP 连通性；任何接口都不返回 SMTP 凭据。
- 生产环境数据库迁移流程已在文档中写明并可重复执行。

**阶段 2**
- 每个用户能拿到唯一专属地址；重置后旧地址失效、新地址可用；停用后新邮件被拒收但历史邮件保留。
- 真实邮件经 Cloudflare 转发后出现在收件箱列表，详情页可读正文与原始邮件。
- 伪造签名、过期时间戳、超大请求体的 webhook 请求分别返回 `401` / `401` / `413`，且不被解析、不写入数据。
- 同一封邮件重复投递只入库一次（幂等）；不同用户持有相同 Message-ID 时互不影响。
- 用户 A 无法读取或删除用户 B 的邮件（返回 `404`）。
- 邮件 HTML 正文在无脚本沙箱中渲染，正文内的脚本与顶层跳转均不执行。
- 超过大小上限的邮件被截断入库且标记 `truncated`，服务不因单封大邮件而崩溃。
- 全部现有测试、typecheck、lint、build 通过。

## Verification

### 阶段 1（已完成，2026-09-28）

**质量门**：`pnpm typecheck`、`pnpm lint`、`pnpm build` 均通过；全部 15 个测试套件 0 失败，其中 `test:auth` 新增 8 个用例覆盖 mailer（含"SMTP 抛错时不向上抛异常"这条关键契约）与邮件模板。

**构建产物核对**：`nodemailer` 已被 trace 进 `.output/server/node_modules`——生产镜像只 `COPY .output`，这是发信在生产能否工作的前提。

**端到端**（本地生产构建 + 独立端口，`MAIL_DEV_LOG_ONLY=true`）：

- 注册后生成验证邮件，链接是**绝对地址**且指向 `/api/auth/verify-email`；点击后 302 到 `/verify-email`，库中 `emailVerified` 由 `f` 变 `t`。
- 找回密码生成重置链接，点击后 302 到 `/reset-password?token=...`；设置新密码后旧密码登录返回 401、新密码返回 200。
- 未登录访问 `/forgot-password`、`/reset-password`、`/verify-email` 均 200；`/applications` 仍 302 回 `/login`（守卫未被削弱）。
- 找回密码连打 4 次：前 3 次 200，第 4 次起 429。`RateLimit.key` 是真实地址（本地为 `::1`）而非 `no-trusted-ip`，说明 `trustedProxies` 配置生效。
- `GET /api/v1/email/health`：非管理员 403；管理员 200，响应体只有连通性结论与发件人，不含任何 SMTP 凭据。
- 找回密码接口对已注册与未注册邮箱返回相同响应（实测未注册邮箱返回 200 与同一句提示）。

**实现期发现并修复的缺陷**：未显式配置 `baseURL` 时 better-auth 会把验证链接生成为 `/verify-email?token=...`——路径指向站内页面而非验证端点，用户点了链接**什么都不会发生且不报错**。已改为显式 `baseURL: APP_URL`，并在 `.env.example` 补充说明。生产 compose 里本就设了 `BETTER_AUTH_URL`，但这是隐式依赖，显式配置后不再依赖环境变量是否漏配。

**测试数据清理**：探针账号、限流记录、测试会话均已删除，并核对真实用户表（2 行）与会话表（55 行历史数据）未被改动。

### 邮箱验证双轨制（2026-09-29 补充）

原设计是"验证不构成使用门槛"。在确认邮件稳定送达收件箱后，改为双轨制：分界时刻之后注册的账号必须先验证邮箱才能登录，存量账号保持宽松。

**本地验证（生产构建 + 独立端口）**：

| 场景 | 结果 |
|---|---|
| 存量账号登录，再访问 `/api/v1/me` | 200 / 200 —— **未被误伤**，这是本次改动最需要守住的不变量 |
| 新账号注册响应 | `token: null`，即注册后不建立会话 |
| 新账号手动登录后访问 `/api/v1/me` | 403 `Email not verified` |
| 新账号点完验证链接后 | `emailVerified` 变 `t`；重新登录后 `/api/v1/me` 返回 200 |

三层结构：`autoSignIn: false` 让注册后不建会话（第一道）；前端 `login()` 拦截并给出"去验证邮箱"的提示（第二道）；中间件对所有 `/api/v1/**` 兜底 403（第三道，防止绕过界面直接调接口）。

区分存量与新账号的依据是**注册时间**而不是 `emailVerified`——后者对两类账号都是 false，无法区分。分界时刻硬编码在 `server/utils/auth.ts`，前端 `use-session.ts` 有一份必须保持同步的副本；若将来要再次调整策略，改这两处即可。

**上线后暴露并修复的缺陷**：最初用 better-auth 的 `autoSignIn: false` 来实现"注册后不建立会话"，结果连带激活了它的**防账号枚举**行为——`shouldReturnGenericDuplicateResponse` 的判据是 `requireEmailVerification || autoSignIn === false`，一旦为真，用**已注册的邮箱**再次注册时接口会返回一个**假的成功响应**：既不建号也不发信，用户看到"注册成功，验证链接已发送"，然后苦等一封永远不会来的邮件。

这个缺陷的迷惑性在于：同一个邮箱走"忘记密码"能正常收到信（同一条 SMTP 通道、同一个发送函数），只有注册路径静默失败，很容易被误判成发信故障。实际复现与修复验证：已存在的邮箱注册返回 `422 USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL`；全新邮箱注册正常建号并发信。

最终改为 `autoSignIn: true`（better-auth 默认值，显式写出以防有人"优化"掉）+ 前端注册成功后主动退出会话，既保住"注册后不进入工作台"，也恢复了"邮箱已存在"的明确报错。

**另一个缺陷（页面白名单与查询串）**：邮件链接跳回的地址是带查询串的（`/reset-password?token=xxx`），而 h3 的 `event.path` **包含查询串**。中间件拿整串去和 `PUBLIC_PAGES` 比对永远匹配不上，于是用户点开重置密码链接会被直接弹回登录页——**没有任何报错，看起来就像"链接坏了"**。同一问题也影响 `/verify-email?error=xxx`（链接失效时用户看不到"已过期"的提示，同样被弹到登录页）。

修复：判断白名单前先剥掉查询串（`event.path.split('?')[0]`）。**教训**：凡是"允许匿名访问的路径清单"这类逻辑，判据必须是 pathname 而不是 `event.path`；后者在很多框架里都包含查询串。

## Risks and open questions

- **邮件送达率**：新域名没有发信信誉，发往 QQ / 163 可能进垃圾箱。缓解：完成服务商域名验证（SPF / DKIM / DMARC）、发信域与链接域同域、纯事务内容；上线后双端种子测试。
- **SMTP 凭据泄露**：被拿去冒充域名群发会导致域名被拉黑。缓解：凭据只在环境变量、不新增任何回传配置的接口、两个发信钩子的收件人恒为账号本人（不存在用户可控收件人）、限流挡住批量触发。
- **Cloudflare 是否强制接管主域名 MX**：官方文档只说"从主域名 Settings 里追加子域名"，未明确承诺"完全不动主域名 MX"，社区说法对立。已实测主域名当前**没有** MX 记录，因此即使被接管影响也为零；实施时改完立刻用 DNS 查询比对，并保留"改用独立域名收信"作为兜底。
- **子域名 catch-all 的归属**：社区有"只有一条 zone 级 catch-all"的说法，与官方"子域名可独立配置"存在张力。两种解读对本用例都成立，不作依赖。
- **免费版 Cloudflare Worker 的 10ms CPU 限额**：在边缘解析 MIME 可能超限。因此**解析放在服务端**，Worker 只做读取与转发。
- **2G 服务器内存**：邮件体积不可控。缓解：Worker 侧截断出网、路由层先判 content-length、字段级字符上限、不存附件内容。
- **收件地址即身份**：地址泄露等于任何人都能往该用户的收件箱投递。地址不可枚举（128 位熵），停用与未知地址返回相同响应不给探测信号；用户可一键重置。
- **`INBOUND_WEBHOOK_SECRET` 在服务器与 Cloudflare Worker 各存一份**：这是整条链路最容易断、且断了最难查的地方（症状是邮件不进来但服务器日志为空）。缓解：写入运维文档，作为部署检查项。
- **在途验证链接的寿命**：邮箱验证 token 是无状态 JWT，更换 `BETTER_AUTH_SECRET` 会让已发出的链接失效。有效期仅 1 小时，影响可控，需在运维文档注明。
