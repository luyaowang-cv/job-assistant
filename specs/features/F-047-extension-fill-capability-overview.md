# F-047: 网申填写能力总纲

> 这是一份**总纲**，不描述单个功能。它定义「插件把一份网申档案填进任意中文网申表单」这件事的能力模型、当前基线、目标与功能点拆分。每个功能点在开工时各自补一套完整的 `Spec → Contracts → Plan → Tasks`（编号见第五节），本文件只负责回答三个问题：**这件事由哪几层组成、现在每层差在哪、按什么顺序补。**

## Goal

让插件在中文网申页面上的填写达到「**不填错、尽量多填、用户看得懂**」，并且这套能力**可度量、可回归、可按站点扩展**。

现状不是"链路不对"——F-034 之后，本地规则先填、残留交给模型、写后回读的骨架已经成立。问题在于每一层都停在"能跑通一次"的程度：规则层靠几条例外判断挡住误填而不是靠机制；结构层靠标签签名计数认控件，同签名就串位；值层没做形态适配，学历/日期/专业经常对不上；速度上做了一整轮重复劳动；用户看不见过程，也看不出哪里出了问题。

## 能力模型

填写不是一次"识别 + 生成"，而是五层流水线，任何一层失守都会让结果显得"插件不会用"。**AI 只在第五层的兜底位置出现，不参与前四层。**

| 层 | 职责 | 现在在哪 | 做对了的标准 |
|---|---|---|---|
| 1 扫描 | 找出页面上所有可见、可写的控件 | `form-page-bridge.js` 的 `scanVisibleFormFields` | 自定义控件、富文本、跨域 iframe、动态渲染表单项一个不漏 |
| 2 识别 | 判定「这个框在问什么」「属于哪块哪条记录」「是谁的信息」 | `form-fill-rules.js` 的打分表 + `BLOCK_ANCHORS`/`resolveRecordIndex` | 认不出就返回空，而不是猜一个 |
| 3 取值 | 从档案取对应值，并转成页面能接受的形态 | `RULES[].read` + 各项 `derived` | 日期/学历/性别/专业/地址在页面上是合法值 |
| 4 写入 | 按控件类型写进去，并回读确认 | `applyFillEntries` / `applyChoiceEntries` | 写完能读回来一致；读不回来就报失败 |
| 5 AI 兜底 | 只对第 2 层没认出的字段补一个值 | `/api/v1/form-fill/stream` | 不发档案正文、不猜敏感项、失败可恢复 |

**贯穿的一层是"呈现"**：进度、页面三色标记、四类报告。它不影响正确性，但决定了用户能不能信任这个工具。

## 当前基线（实测，2026-10-19）

| 维度 | 现状 | 证据 |
|---|---|---|
| 识别覆盖 | 大易 `resumeOperation` 页 32 个字段 → 24 个可识别；剩余 8 个是"档案没数据/规则不填"而非认不出 | 用户导出的字段结构 + 本地规则回放 |
| **误填** | 拾星改造版会把「紧急联系人姓名/电话」填成本人；`extension/` 目前不填，但靠 `isDescriptorCompatible` 一行正则与 `GENERIC_ALIASES` 生效条件**两处巧合** | 用 5 个字段直接喂 `buildFillPlan` 实测 |
| 结构定位 | 写入后用「标签签名计数」判断哪些是刚填的；两段经历的两个「开始时间」签名相同，会互相顶替 | `main.ts` 的 `appliedSignatureCounts` |
| 值形态 | 学历/日期/专业靠字符串包含匹配；日期分片与自定义下拉各有实现，但缺少统一的"值→控件形态"适配 | `form-page-bridge.js` 的 `fillSelect`、`dateUnit` 分支 |
| 速度 | 一次填写 = **2 轮全页扫描 + 2 轮规则匹配**（第二轮只为确认"写进去了吗"） | `main.ts` 中两次 `scanEveryFrame` / `buildFillPlan` |
| 可见性 | 页面只有绿色标记；进度只有一行「AI 正在填写…」 | `form-page-bridge.js:599` 只有一种颜色 |
| 报告 | 「模型没答」「未尝试」「写入失败」「需确认」混在一起 | `renderFillReport` |
| 回归 | 124 条测试，全部通过 | `pnpm test` |

## 目标（能力级，可度量）

- **G1 误填率为 0。** 定义：写进页面的值与该字段语义不符的次数。以"紧急联系人/家庭成员/推荐人"三类他人字段、两段同结构经历、跨域同名控件为必测场景。**这是唯一不可让步的指标**——填错比填不上贵得多。
- **G2 确定字段本地覆盖率 ≥ 90%。** 定义：姓名、手机、邮箱、学校、专业、学历、公司、职位、起止时间这类"档案里一定有、页面上一定有"的字段，由本地规则而非模型填上的比例。
- **G3 本地阶段 ≤ 1 秒。** 从点击到本地规则的答案全部写入页面（不含模型等待），30–40 字段的页面。
- **G4 每次填写都有可读的四类报告**：模型没答 / 未尝试 / 写入失败（附原因）/ 需手动确认（附原因），各自计数并列出字段名。
- **G5 新站点适配成本 ≤ 30 分钟 + 1 份导出结构。** 不需要改代码就能覆盖的站点占比逐次提高；需要改代码时，改动必须落成一条回归夹具。
- **G6 测试基线不退化。** 现有 124 条全绿，每个功能点新增用例覆盖其验收标准。

## 功能点拆分

九个功能点，P0 是"会填错/会串位"的根，必须先做；P1 决定体验上限；P2 是工程化与长尾。

| 编号 | 功能点 | 解决什么 | 优先级 | 依赖 |
|---|---|---|---|---|
| F-048 | 归属与冲突拦截 ✅ | 谁的姓名/电话；两条规则打架时不猜；同一个值不跨域写入 | P0 | — |
| F-049 | 区块与记录的稳定定位 ✅ | 教育/实习/项目分块；第 N 块对应第 N 条记录（含已填过的块） | P0 | — |
| F-052 | 一次扫描与增量回读 ✅ | 去掉第二轮全页扫描与第二轮规则匹配 | P0 | F-048、F-049 |
| F-050 | 控件写入与回读覆盖 ✅ | 自定义下拉、可搜索下拉、日期分片、富文本、单选组 | P1 | F-049 |
| F-053 | 顺序写入与逐字段确认 ✅ | 按页面从上到下写；每写一个当场回读 | P1 | F-052 |
| F-054 | 进度、三色与报告分区 ✅ | `正在填写 12/34`；绿/橙/红；四类报告 | P1 | F-053 |
| F-051 | 值形态适配 ✅ | 学历选最接近的合法选项、日期按控件要求、数字框形状（专业级联未做） | P2 | F-050 |
| F-055 | 失败恢复与限流 ✅ | 429/超时/中断时保留已写、明确告知、可继续 | P2 | F-052 |
| F-056 | 站点适配流程与回归夹具 ✅ | 导出结构 → 补规则 → 回放比对，固化成流程 | P2 | F-048~F-054 |

**建议执行顺序**：F-048 → F-049 → F-052 → F-053 → F-054 → F-050 → F-051 → F-055 → F-056。前三个做完，用户最痛的三件事（填错、串位、慢）就都解决了。

## Out of scope（总纲层面）

- **自动投递、自动翻页、批量提交**：产品宪章明确不做。
- **海外 ATS 的字段适配**（Workday / Greenhouse / Lever 等）：host 权限保留，但别名与控件不做专门适配，走通用规则。
- **把填写流程搬出 popup**：这是宿主架构问题，独立立项。本次只保证页面上的标记在 popup 关闭后仍然可见。
- **后台常驻监听页面变化**：不做，仍然由用户显式点击发起。
- **服务端 `finish_reason` 截断识别与成本常数校准**：契约里已记为已知局限，属服务端改动，独立一期。

## 度量方法

G1/G2 用**回放 + 真机双证**：拿真实站点导出的字段结构喂给规则层，统计"识别/冲突/落空"三类计数；再在真机上跑一次，逐项核对写进页面的值有没有错。

G3 用 popup 内的计时打点（本地写入开始 → 全部 `applied`），连续三次取中位数。

G4/G5 看报告本身：报告分不出四类就说明没做到。

所有度量结果回写到对应功能点的 spec 验收段；本总纲的目标值不在功能点执行后修改，只在证据表明目标本身不合理时修订，并注明原因。

## 首次真机结果（2026-10-20，顺丰简历页）

一次填写：**已填 15 / 跳过 45 / 需处理 15（写入失败 0、模型没答 13、需手动确认 2）**。

- 本地规则这部分**没有出现误填**：性别、证件类型、证件号码、民族、政治面貌、期望城市、籍贯、院系、职务、项目职责都是本人信息；他人字段没有继承本人值。
- 四类报告按设计分开，`写入失败 0` 说明写后回读全部通过。
- **AI 部分整段失败**：流式请求 429 后立即切到分批，分批撞同一份额度又 429，13 个字段全丢。已修（见 F-055 真机记录）。
- 45 项"已有内容"符合预期——这是简历编辑页，页面带着之前的草稿。

**G1** 在这一次里成立（无误填）；**G2/G3** 仍无有效数据（这次 AI 全程失败，覆盖率与耗时都不具代表性）。
