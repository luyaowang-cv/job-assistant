# F-053: 顺序写入与逐字段确认

> 属于 F-047 总纲的 P1 功能点。

## Goal

用户要的是"从上到下、一个框一个框填"：能看见它在动，也知道它填到哪了。

**核对代码后，这条功能点原本设想的 bug 不存在。** 总纲里写的"选择类控件按到达顺序写"是我的误判——`applyChoiceEntries` 和 `applyFillEntries` 一样，遍历的是 `allControls`（页面顺序），用 `byId` 查有没有答案要写；传入的 `entries` 顺序对写入顺序没有影响。

所以本次**不改写入逻辑**，交付两样东西：把这个不变量用测试锁住（防止将来有人把它"优化"成遍历答案），以及把真实存在的边界写清楚。

### 现状（已成立）

- **两个写入器都按页面顺序写**：`applyFillEntries` 的 `for (const { element, index } of controls)`、`applyChoiceEntries` 的 `allControls.forEach(...)`，都是先按页面位置取控件、再查答案。
- **逐字段确认**：每个字段写完进 `deferredReadbacks`，批次结束时统一审计；失败字段带独立原因。**不改成"每写一个立刻回读"**——同一批次里后写入的值可能影响前面的控件状态，批末统一读反而更准。
- **用户能看到它在动**：每个控件写入前会 `scrollIntoView` + 90ms 高亮，形成从上到下的可见节奏。

### 真实存在的边界（记录，不修）

- **文本与选择两类写入是并行的**：`flushFills` 用 `Promise.all` 同时调 `applyFillEntries` 与 `applyChoiceEntries`。两者各自内部有序，但**跨类型的先后不保证**——页面第 5 位的单选框可能与第 10 位的文本框同时写。
- **批次之间按到达顺序**：流式回答按模型返回的批次落盘。批次内有序，批次间由模型决定。强行全局有序等于攒齐再写，那就放弃流式了。

## User scenarios

- 无论模型以什么顺序回答，同一批次内的控件都按页面从上到下写入。
- 某个控件写失败时，报告里那一条带具体原因，而不是整批一句"未能应用"。

## In scope

- 源码级断言：两个写入器都遍历控件列表而非答案列表；`byId.get(...)` 的查表模式存在。
- 在契约里记录"批次内保证顺序、批次间与跨类型不保证"这条边界。

## Out of scope

- 合并两个写入器为单一顺序通道（改动大、收益小，跨类型乱序在 90ms 高亮节奏下几乎看不出来）。
- 跨批次全局排序。
- 逐字段即时回读（理由见上）。

## 验收标准

- AC-1：源码级断言——`applyFillEntries` 遍历 `controls`、`applyChoiceEntries` 遍历 `allControls`，两者都不存在"遍历 entries 直接写"的主循环。
- AC-2：把任一写入器改成遍历 `entries` 时，AC-1 的断言失败（反向验证）。
- AC-3：现有 138 条测试全绿；北森 dump 回放计数不变。
- AC-4：契约里记录跨类型并行与跨批次乱序两条边界。

## Risks and open questions

- **不变量靠测试而非代码结构保证**：将来若有人把写入器改成"遍历答案"，顺序会静默退化。AC-1/AC-2 是唯一防线。
- **跨类型并行的视觉效果**：目前靠 90ms 高亮掩盖；若将来把高亮去掉，用户可能察觉到"跳着填"。

## 实施记录（2026-10-19）

**调查结论**：总纲把「选择类控件按到达顺序写」列为待修问题，核对 `applyChoiceEntries` 函数体后不成立——它遍历 `allControls` 并用 `byId.get(fieldId)` 查答案，与 `applyFillEntries` 同构。写入顺序与传入顺序无关。

**因此没有改任何写入逻辑**，只补了一条源码级断言（`fill-flow.test.js`）：两个写入器都必须遍历控件集合、且存在 `byId.get(` 查表。

**反向验证**：把 `applyChoiceEntries` 的 `allControls.forEach((element) => {` 临时改成 `entries.forEach(...)`，断言立即失败并报「选择写入应当遍历控件列表」；还原后全绿。证明这条断言不是永远绿的摆设。

**验收**：测试 138 → **139 全绿**；本次不改行为，北森 dump 回放计数必然不变（仍跑过一次确认）。

**教训**：总纲里的判断也会错。这条功能点原本计划"加排序"，实际是给不存在的问题加代码——**先读函数体再动手**，比照着计划做更重要。
