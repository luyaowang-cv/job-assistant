# F-011: 候选人资料、网申档案与简历版本重构

## Goal

将当前容易混淆的“档案资料”拆分为稳定的个人主档案、可变的网申档案和可多版本保存的简历内容；使官网固定资料能够自动填写，同时避免不同岗位方向的简历内容相互覆盖。

## User scenarios

1. 用户只维护一份个人主档案，包含个人基本信息、教育背景、身份证号码和紧急联系人等长期事实。
2. 用户创建“前端大厂”“AI 前端”“Agent 开发”“国央企”等网申档案，只设置求职方向、期望地点、招聘来源、内推码、到岗时间和默认简历版本。
3. 用户在线编辑并保存多份简历版本；每份只保留该方向需要展示的项目、实习、技能与校园经历。
4. 用户在官网点击填写并选择网申档案后，插件自动合并个人主档案、网申档案和关联简历版本：明确字段由本地规则填写，开放问题再交给 AI。
5. 用户修改手机号、学校或毕业信息后，所有未覆盖的网申档案立即使用新值，无须逐份修改。

## In scope

- 将产品术语从含混的“档案资料”调整为“网申档案”；它不是简历版本。
- 扩展 `PersonalProfile` 为唯一的个人主档案，分组维护基础与联系、证件与紧急联系、教育主记录；最高学历、最高学位等由教育记录推导，除非用户显式覆盖。
- 将 `ApplicationProfile` 收敛为网申档案：名称、目标标签、期望工作地点/薪资、可到岗时间、招聘来源、内推码、默认 ResumeVersion；不再存储个人固定资料和完整经历副本。
- 保留 `Resume`/`ResumeVersion` 作为在线编辑后的简历版本资产。经历素材库/结构化编辑器在单独 Feature 中实现。
- 新增官网自动填写的已解析候选人资料视图：个人主档案 + 网申档案 + 被选简历版本。完整个人主档案可由用户明确授权给 AI 使用，用于补齐本地规则未覆盖的表单字段。
- 为现有网申档案提供非破坏性迁移：已有 basics/educations 保留为覆盖值，迁移后仅将用户明确确认的固定资料写回个人主档案。

## Out of scope

- 不自动提交、点击同意声明、支付、上传文件、发送消息或跳转网页。
- 不把页面既有输入值、Cookie、密码、验证码、上传文件或浏览器历史发送给 AI、记录到请求日志或返回给扩展报告。
- 不在本 Feature 中实现多用户、云同步、简历 PDF/DOCX 导入导出或完整经历素材库编辑器。
- 不根据 AI 猜测或补造任何个人、教育、项目或工作事实。

## Acceptance criteria

1. 工作台具有清晰独立的“个人主档案”“网申档案”“简历版本”入口；界面文案不再将网申档案称作简历版本。
2. 用户只需在个人主档案中维护一次固定资料和教育主记录；网申档案创建页不重复要求填写这些字段。
3. 每个网申档案可关联一个默认简历版本，并仅维护随投递策略变化的字段。
4. 官网填写前，扩展读取的已解析资料能同时包含主档案、网申档案和默认简历版本；固定字段优先由本地规则自动填写。
5. 身份证号码和紧急联系人在页面标签明确时优先由本地规则填写；本地规则未覆盖时，AI 可读取用户保存的完整主档案补齐普通文本或下拉字段。插件报告不显示实际值。
6. 所有 API 输入/输出均由 Zod 约束；迁移不删除已有 ApplicationProfile、Resume 或 ResumeVersion；typecheck、迁移测试和扩展 fixture 验证通过。

## Risks and open questions

- 现有 ApplicationProfile 已含方向性经历字段。第一期只能保持兼容读取，不能未经用户确认自动判定哪些内容应成为个人主档案或简历素材。
- 用户确认个人使用场景下允许 AI 读取完整主档案并自动填写身份证和紧急联系信息；页面已有值、认证/验证、上传和提交行为仍不在范围内。
- “默认简历版本”需要 ResumeVersion 的稳定标识与归属校验；若尚无版本，网申档案可保存但必须提示用户未关联简历。
